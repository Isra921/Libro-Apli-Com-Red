Unidad III · Tema 3.1

Sockets orientados a conexión no bloqueantes

La entrada y salida no bloqueante (Non-blocking I/O) y la multiplexación de canales permiten que un único hilo de ejecución atienda eficientemente a miles de conexiones de red simultáneas sin suspenderse esperando datos en tránsito.

3.1.1Limitaciones del modelo bloqueante y el desafío C10K

En el modelo clásico de sockets bloqueantes con hilos (visto en las unidades anteriores), cada hilo que atiende a un cliente se suspende al invocar read() hasta que el host remoto transmita datos. Si un cliente conectado permanece inactivo durante varios minutos, el hilo del servidor permanece dormido pero consumiendo memoria de pila (stack) y recursos del sistema operativo.

A finales de la década de 1990, Dan Kegel formuló el denominado desafío C10K (Concurrent 10,000 Connections): diseñar un servidor de red capaz de mantener 10,000 conexiones concurrentes en hardware comercial sin colapsar. En este escenario, crear 10,000 hilos del sistema operativo requeriría más de 10 GB de RAM únicamente en espacio de pila, provocando que la CPU pase más tiempo realizando cambios de contexto que procesando datos útiles.

La solución no bloqueante

En lugar de que el hilo espere pasivamente a que los datos lleguen a un socket específico, el sistema operativo le notifica al hilo qué sockets tienen datos listos para ser leídos o enviados. Esto constituye el corazón de la multiplexación de entrada/salida (I/O Multiplexing).

3.1.2La arquitectura de Java NIO: Canales y Búferes

A partir de Java 1.4, se introdujo el paquete java.nio (New I/O / Non-blocking I/O) estructurado sobre tres abstracciones clave:

  • Canales (Channels): A diferencia de los streams tradicionales unidireccionales (InputStream y OutputStream), los canales representan conexiones bidireccionales abiertas hacia entidades como archivos o sockets de red. Pueden configurarse explícitamente en modo no bloqueante mediante channel.configureBlocking(false).
  • Búferes (Buffers): Bloques continuos de memoria administrados a través de la clase ByteBuffer. Toda operación de lectura o escritura en un canal pasa obligatoriamente por un búfer intermedio.
  • Selectores (Selectors): Componente que multiplexa múltiples canales de red en un solo hilo examinando eventos de preparación en el kernel subyacente (utilizando llamadas al sistema nativas eficientes como epoll en Linux, kqueue en macOS o IOCP en Windows).

3.1.3Manejo y ciclo de vida de los búferes de memoria (ByteBuffer)

Un ByteBuffer opera con tres punteros internos fundamentales que gobiernan la lectura y escritura de bytes:

  1. capacity (capacidad): El tamaño total máximo de bytes asignados al búfer.
  2. position (posición): El índice del siguiente byte que se leerá o escribirá.
  3. limit (límite): El límite actual hasta donde se pueden leer o escribir datos válidos.

Para alternar entre escribir datos provenientes de la red y leerlos para su procesamiento, se utiliza la operación de volteo o inversión: buffer.flip(), que ajusta el límite a la posición actual y reinicia la posición a cero: 

ByteBuffer buffer = ByteBuffer.allocate(1024); // Asignación de 1 KB en RAM

// 1. Canal lee de la red y escribe en el búfer
int bytesLeidos = socketChannel.read(buffer);

// 2. Voltear el búfer para preparar la lectura de los datos recién cargados
buffer.flip();

// 3. Procesar los bytes válidos del búfer
while (buffer.hasRemaining()) {
    byte b = buffer.get();
    // Procesar byte...
}

// 4. Limpiar o compactar para la siguiente lectura
buffer.clear();

3.1.4El Selector y las claves de selección (SelectionKey)

Un Selector se registra con los canales no bloqueantes indicando qué tipo de operaciones de red le interesan al servidor para cada canal. Las cuatro operaciones estandarizadas son:

  • SelectionKey.OP_ACCEPT: El ServerSocketChannel tiene una conexión de cliente entrante lista para ser aceptada.
  • SelectionKey.OP_CONNECT: El SocketChannel del cliente ha completado exitosamente la conexión al servidor remoto.
  • SelectionKey.OP_READ: El socket receptor tiene datos listos en su búfer de red para ser leídos sin bloquearse.
  • SelectionKey.OP_WRITE: El canal de red tiene espacio en su búfer de salida y puede aceptar nuevos bytes para transmitir.

3.1.5Implementación de un servidor no bloqueante con bucle de eventos

El siguiente ejemplo muestra la estructura fundamental de un servidor TCP no bloqueante capaz de atender múltiples clientes concurrentes en un único hilo de ejecución: 

import java.net.InetSocketAddress;
import java.nio.ByteBuffer;
import java.nio.channels.*;
import java.util.Iterator;

public class ServidorNoBloqueanteTCP {
    public static void main(String[] args) throws Exception {
        Selector selector = Selector.open();
        ServerSocketChannel serverChannel = ServerSocketChannel.open();
        
        serverChannel.bind(new InetSocketAddress(9000));
        serverChannel.configureBlocking(false); // Canal en modo no bloqueante
        serverChannel.register(selector, SelectionKey.OP_ACCEPT);

        System.out.println("Servidor no bloqueante iniciado en puerto 9000...");

        while (true) {
            selector.select(); // Espera hasta que al menos un canal tenga eventos listos
            Iterator<SelectionKey> keys = selector.selectedKeys().iterator();

            while (keys.hasNext()) {
                SelectionKey key = keys.next();
                keys.remove(); // Muy importante: remover la clave procesada

                if (key.isAcceptable()) {
                    SocketChannel clientChannel = serverChannel.accept();
                    clientChannel.configureBlocking(false);
                    clientChannel.register(selector, SelectionKey.OP_READ);
                    System.out.println("Cliente aceptado: " + clientChannel.getRemoteAddress());
                } else if (key.isReadable()) {
                    SocketChannel clientChannel = (SocketChannel) key.channel();
                    ByteBuffer buffer = ByteBuffer.allocate(256);
                    int leidos = clientChannel.read(buffer);

                    if (leidos == -1) {
                        clientChannel.close(); // Conexión cerrada por el cliente
                    } else {
                        buffer.flip();
                        // Eco de respuesta no bloqueante
                        clientChannel.write(buffer);
                    }
                }
            }
        }
    }
}
