Sincronía de hilos

En los servidores de red concurrentes, la atención simultánea de múltiples clientes que leen y modifican recursos compartidos en memoria exige mecanismos rigurosos de sincronización para evitar condiciones de carrera y corrupción de datos.

2.1.1Instrucciones atómicas y coherencia de memoria

Una operación se considera atómica cuando se ejecuta como una unidad indivisible e ininterrumpible: o se completa en su totalidad o no se ejecuta en absoluto, sin que ningún otro hilo o procesador pueda observar un estado intermedio inconsistente.

En lenguajes de alto nivel como Java o C++, operaciones aparentemente simples como un incremento contador++ no son atómicas. A nivel de máquina, este operador se descompone en tres instrucciones secuenciales distintas:

  1. Lectura (Read): Cargar el valor de la variable desde memoria RAM al registro del procesador.
  2. Modificación (Modify): Incrementar en 1 el valor en el registro de la CPU.
  3. Escritura (Write): Volcar el nuevo valor del registro a la memoria principal.

Si el planificador del sistema operativo realiza un cambio de contexto (context switch) entre la lectura y la escritura mientras otro hilo de red ejecuta la misma instrucción, se produce una pérdida de actualizaciones. Para resolver esto a nivel de hardware, se emplean primitivas atómicas del procesador como Compare-And-Swap (CAS), implementadas en Java mediante clases como AtomicInteger o AtomicLong: 

import java.util.concurrent.atomic.AtomicInteger;

// Contador de conexiones activas completamente atómico y seguro entre hilos
AtomicInteger clientesConectados = new AtomicInteger(0);

// Incremento seguro garantizado a nivel de instrucción de máquina
int actual = clientesConectados.incrementAndGet();

2.1.2Sección crítica y condiciones de carrera en servidores de red

Una sección crítica es cualquier segmento de código que accede a una estructura de datos o recurso compartido (como la lista de clientes en un chat, la tabla de sesiones activas o un archivo de registro) donde al menos uno de los hilos realiza operaciones de escritura.

Cuando dos o más hilos concurrentes intentan entrar a la sección crítica y el resultado final depende del orden temporal impredecible de ejecución de sus instrucciones, se presenta una condición de carrera (Race Condition).

Peligro en servidores de red

Las condiciones de carrera son extremadamente elusivas: pueden manifestarse únicamente cuando el servidor se somete a altos volúmenes de tráfico concurrente, produciendo desconexiones espontáneas, valores duplicados o corrupción silenciosa de transacciones.

2.1.3Candados (Locks) y monitores

Para proteger una sección crítica, se implementan mecanismos de bloqueo (Locks). Un hilo debe adquirir el cerrojo o llave antes de ingresar al bloque protegido; si el cerrojo ya se encuentra ocupado por otro hilo, el invocador se suspende hasta que el poseedor libere el candado.

En la plataforma Java, la sincronización se apoya en el concepto de Monitor mediante la palabra reservada synchronized, o bien a través de la interfaz explícita Lock del paquete java.util.concurrent.locks: 

import java.util.concurrent.locks.ReentrantLock;

public class GestorSalasChat {
    private final ReentrantLock cerrojo = new ReentrantLock();

    public void difundirMensaje(String mensaje) {
        cerrojo.lock(); // Adquisición exclusiva del candado
        try {
            // Sección crítica: iteración y escritura a los sockets clientes
            for (Socket cliente : listaClientes) {
                enviarTrama(cliente, mensaje);
            }
        } finally {
            cerrojo.unlock(); // Siempre liberar en bloque finally
        }
    }
}

2.1.4Principio de exclusión mutua (Mutex)

La exclusión mutua (abreviada comúnmente como Mutex) es la propiedad fundamental que garantiza que, en cualquier instante dado, a lo sumo un solo hilo puede encontrarse ejecutando dentro de una sección crítica específica.

Para que una solución de exclusión mutua sea formalmente correcta y segura, debe satisfacer tres condiciones indispensables postuladas en la teoría de sistemas concurrentes:

  • Exclusión mutua estricta: Ningún par de hilos puede encontrarse simultáneamente en la sección crítica asociada al mismo recurso.
  • Ausencia de interbloqueo (Deadlock): Si ningún hilo está dentro de la sección crítica y varios intentan entrar, el sistema no debe congelarse indefinidamente; la decisión de quién entra debe resolverse en tiempo finito.
  • Ausencia de inanición (Starvation / Progreso Justo): Ningún hilo debe esperar indefinidamente para obtener el acceso si otros hilos entran y salen repetidamente.

2.1.5Semáforos (Semaphores contadores y binarios)

Introducidos originalmente por Edsger Dijkstra en 1965, los semáforos son variables protegidas de tipo entero acompañadas de dos operaciones primitivas atómicas:

  • acquire() (históricamente operación P): Decrementa el valor del semáforo. Si el contador es menor o igual a cero, el hilo se bloquea en espera de permisos disponibles.
  • release() (históricamente operación V): Incrementa el valor del semáforo y despierta a uno de los hilos en espera.

En servidores de red, los semáforos resultan idóneos para limitar el número máximo de transferencias simultáneas o restringir el consumo de ancho de banda: 

import java.util.concurrent.Semaphore;

// Limitar a máximo 50 descargas concurrentes simultáneas en el servidor de archivos
Semaphore limiteDescargas = new Semaphore(50, true); // true = equidad FIFO

public void descargarArchivo(Socket socket) {
    limiteDescargas.acquire(); // Bloquea si ya hay 50 descargas en curso
    try {
        transmitirArchivo(socket);
    } finally {
        limiteDescargas.release(); // Libera el permiso para el siguiente cliente
    }
}

2.1.6Pools de hilos (Thread Pools) y arquitectura ExecutorService

En un diseño ingenuo de servidor multihilo, se crea un hilo nuevo cada vez que un cliente se conecta: new Thread(clienteHandler).start(). Este modelo de hilo por conexión (Thread-per-connection) colapsa rápidamente bajo carga pesada:

  • Sobrecarga de creación y destrucción: Asignar la pila de llamadas (call stack, típicamente 1 MB) y la memoria del sistema operativo por cada conexión consume tiempo y recursos considerables.
  • Agotamiento de memoria (OutOfMemoryError): Un ataque o ráfaga de 5,000 conexiones simultáneas agotaría la memoria antes de procesar una sola petición.

Para resolver esto, la arquitectura estándar emplea una piscina o conjunto de hilos (Thread Pool). Un pool mantiene un conjunto fijo o dinámico de hilos trabajadores (worker threads) que permanecen vivos en memoria, tomando tareas de una cola de bloqueo (BlockingQueue): 

import java.net.ServerSocket;
import java.net.Socket;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ServidorConcurrentePool {
    public static void main(String[] args) throws Exception {
        ServerSocket server = new ServerSocket(8080);
        // Pool administrado de 20 hilos trabajadores reutilizables
        ExecutorService pool = Executors.newFixedThreadPool(20);

        System.out.println("Servidor multihilo con pool activo en puerto 8080...");
        while (true) {
            Socket cliente = server.accept();
            // La tarea se encola y es despachada por un hilo disponible del pool
            pool.execute(new ManejadorCliente(cliente));
        }
    }
}
